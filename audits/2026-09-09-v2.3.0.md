# v2.3.0 audit — 2026-09-09

Reviewed commit: `ace78893216948bc3d475fc901dc58e035e95b5e`.

Three confirmed P2 defects; no confirmed P0/P1 finding. Production source and dependencies were not modified. The audit added this report and an inert reproduction fixture.

## Findings

### 1. P2 — Failed OAuth authentication bypasses token rate limiting

Location: `src/http/app.ts:118` (pre-check), `src/http/app.ts:178` (downstream OAuth router).

The custom `/token` middleware returns 401 for unknown clients, missing credentials, and incorrect secrets before the SDK's token router runs. The SDK applies its 50-requests-per-15-minutes limiter inside that downstream router. Consequently, unsuccessful secret guesses never consume that quota. This removes throttling from the shared client secret that protects public static-client deployments. It permits unrestricted authentication attempts and associated request-processing load; it does not itself bypass secret verification.

**Reproduction:** start the real Express/OAuth application on loopback with `trustProxy: false`, then send 55 sequential requests with the same known client ID and an incorrect secret. Requests 51–55 all returned **401**, not **429**. All credentials were synthetic.

**Fix:** rate-limit `/token` before any credential rejection path, while preserving the constant-time comparison. Avoid counting valid requests twice if retaining the SDK limiter. Add HTTP coverage for wrong secrets, unknown clients, and missing credentials, plus the successful exchange path.

### 2. P2 — Merged timelines cross the guaranteed ordering limit

Location: `src/tools/entries.ts:77` and `src/tools/entries.ts:168`.

`includeLinkedPersons` fetches at most 100 entries per party. Its schema promises a global top-100 ceiling, but the result uses an uncapped `merged.slice(start, start + perPage)`. The pagination helper also returns early whenever the concatenated candidate count exceeds the requested window, before checking the ceiling.

When multiple parties have enough history, this exposes positions beyond 100 even though newer entries from a busy party were never fetched. The caller receives older entries as though they occupied the next chronological positions, with a continuation cursor that compounds the omission.

**Reproduction:** one organisation has 101+ recent entries, while a linked person has 100 older entries. With `page: 2, perPage: 75`, the tool returns **75 entries and `nextPage: 3`**. Its documented contract requires **25 entries and no next page**. The existing ceiling tests use an empty organisation feed, so their merged candidate array never exceeds 100 and does not expose this defect.

**Fix:** cap both slicing and cursor generation at the global ceiling, including windows that start beyond it. Test with at least two nonempty feeds and an upstream next-page signal. Alternatively, implement additional upstream pagination to support a larger globally ordered window.

### 3. P2 — Task expiry leaves untracked, uncancellable batch writes running

Location: `src/tasks/store.ts:140`.

The TTL callback removes ownership and the registered AbortController without aborting it. The SDK independently deletes the task. A batch handler still holds its un-aborted signal and continues claiming queued writes after the task disappears. Its eventual result cannot be stored because ownership is gone; the background runner swallows that store error.

This affects the opt-in `MCP_TASKS_ENABLED` path when execution exceeds the requested TTL (the minimum accepted TTL is one second). The caller cannot inspect the result or cancel the remaining work, and removing the owner entry frees task quota while execution is still consuming resources. Retrying an apparently missing task can overlap the original work.

**Reproduction:** submit `batch_complete_task` with three IDs, concurrency 1, and `ttl: 1000`; hold the first mocked Capsule request pending until after expiry. Both `tasks/get` and `tasks/cancel` then fail. Releasing the first request starts **both remaining writes**: three total requests, although only one was in flight before expiry.

**Fix:** either abort pending work before eviction, or track active execution and cancellation separately from result-retention expiry. In either design, quota accounting must continue to cover running work. Define and test the behavior for a task expiring during a batch; already-dispatched writes can complete, but must not trigger uncontrolled further fan-out.

## Dependency observation

The installed dependency chain resolves SDK 1.30.0 and `@hono/node-server` 2.0.11 to Hono 4.13.2. The advisory database lists 4.13.5 as patched for:

- [Dot-notation body parsing memory exhaustion](https://github.com/advisories/GHSA-g6gw-c38x-mqfc).
- [Query parsing after URL fragments](https://github.com/advisories/GHSA-crvj-82cr-hjcx).
- [Static generation output-directory traversal](https://github.com/advisories/GHSA-gqvv-2mrq-wpjv).

The reviewed server uses Express body parsing and the SDK's Web Standard transport through the Hono Node adapter. No use of the affected Hono body/query parsers or static generator was found in those runtime paths. Treat this as dependency maintenance, not a demonstrated exploit against capsulemcp. Updating the override floor and lockfile to a patched version would clear the known advisories for lockfile-based installs; validate the resulting dependency graph. The current high-severity CI threshold deliberately does not fail on moderate advisories.
